# ADR-007: Serve one UI with local and browser compute

Status: Accepted; tier 1 shipped, tier 2 and codec matrix unverified.
Date: 2026-11-05.

## Context

A second UI duplicates design and text work. A hosted compute service would
hold user inputs and introduce operating cost. Browser compute also has codec,
performance and numeric parity limits that need measurements.

## Decision

I use one plain TypeScript DOM UI in web/, built by Vite for GitHub Pages
(the published root) and the wheel (copypaw/app/static/). Do not add Gradio or a
UI framework. LocalBackend calls the loopback JSON API and Python reference;
TabBackend runs the TypeScript port in a module Web Worker behind ComputeBackend.

I ship only the browser tiers that pass numeric parity and performance checks. Tier 1
covers gallery motion and drawing deformation; tier 2 adds clip pose processing.
Failure of tier 1 also excludes tier 2. Tier 1 now ships; tier 2 remains unshipped.
The local app supplies local video decoding and optional accurate mode.

Tier 2 models belong in my public Hugging Face model repository, pinned
by revision and SHA-256. Pages has a site-size budget. The GitHub release asset
request recorded below lacks the required browser CORS response. Model
publication is pending.
Pages hosts the gallery at its root; Codespaces is for contributors.

## Consequences

Python remains the reference for the port. The same goldens must establish
parity before shipping. Device and codec checks need gallery and local-app paths
when a clip cannot run in the tab. H.264 encode support enables MP4 export;
a measured lack of support selects GIF export for that browser.

## Day-one evidence, 2026-11-05

Playwright 1.64.1 installed Chromium 156.0.8078.4 (build 1248), WebKit 27.2
(build 2370) and Firefox 157.0 (build 1555). All three fail to launch in a
session without a display: Chromium's Mach port registration is denied, WebKit exits 134, and
Firefox exits with SIGABRT. H.264 encoding, H.264 and HEVC WebCodecs decoding,
and HEVC video-element decoding are pending for every browser. No GIF-only
browser decision can be made from these launch failures. docs/verification.md,
item 5 contains the exact probe and verification commands.

Initial registry checks found Vite 8.3.6 versus pinned 8.3.5 and CodeQL action
v4.39.3 versus pinned v4.39.2. Those observations are historical, not current
registry guarantees. I hold TypeScript at 6.0.3 for typescript-eslint
compatibility; the same check found 7.0.2 available.

## Release-asset CORS evidence

On 2026-11-06 UTC I requested the versioned
[YOLOX-tiny release asset](https://github.com/Megvii-BaseDetection/YOLOX/releases/download/0.1.1rc0/yolox_tiny.onnx)
with method `GET` and these explicit request headers:

```http
Origin: https://copypaw.github.io
Range: bytes=0-0
User-Agent: Copypaw-documentation
```

The final redirected response from `release-assets.githubusercontent.com`
returned these relevant headers:

```http
HTTP 206 Partial Content
Date: Fri, 06 Nov 2026 01:07:50 GMT
Content-Length: 1
Content-Type: application/octet-stream
Content-Range: bytes 0-0/20219662
```

`Access-Control-Allow-Origin` was absent. The origin string is a test input,
not evidence of a deployed site. This response cannot authorize a browser to
read the model cross-origin. It supports avoiding this tested asset route for
browser model delivery, not a permanent assertion about every release asset.

To inspect a new response without launching a browser:

```sh
mkdir -p /tmp/copypaw-verification
curl -fL --range 0-0 --max-time 45 \
  -H 'Origin: https://copypaw.github.io' \
  -H 'User-Agent: Copypaw-documentation' \
  --dump-header /tmp/copypaw-verification/yolox-cors.headers \
  -o /tmp/copypaw-verification/yolox-byte \
  'https://github.com/Megvii-BaseDetection/YOLOX/releases/download/0.1.1rc0/yolox_tiny.onnx'
```

## Tier results

Updated 2026-11-12: tier 1 ships a drawing segmenter, template fit and snap,
planar retargeting, outline mesh, contact IK, ARAP and WebGL2 rendering. The
worker runs these in web/src/compute/; the built-in dog_walk motion needs no
pose-model download or server. Parity fixtures come from
`scripts/export_web_parity.py`; web/src/compute/parity.test.ts checks the mesh,
retargeted joints and handles against Python. web/e2e/tab.spec.ts exercises
sample animation in a real browser. The Python engine uses about 1000 interior
mesh vertices, with outline vertices added according to the drawing's shape.

The cold-start command defaults to tier 1 and waits for a completed live
canvas or a new exported video. The Pages workflow audits the built artifact
that it deploys, at the published root path. The 30 s gallery budget describes a
machine with a GPU, so a run on a software WebGL renderer prints its time and the
renderer but is not gated on the budget.

Tier 2 remains unshipped: the tab has no clip input, pose/identity/smoothing/
contact pipeline or ONNX Runtime Web dependency. The local app provides clip
capture and file exports. `scripts/quantize_models.py` can produce and compare
ViTPose-S variants, but no browser variant has been chosen or published.

## Not independently confirmed

I have not executed a browser model fetch against this route or checked CORS on every
model host. The header observation does not establish preflight behavior,
future responses or Hugging Face browser delivery. Browser codec support,
the cross-browser codec matrix and tier performance outside the tested
Chromium path still require the commands in the verification notes.
