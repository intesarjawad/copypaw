# ADR-004: Render in a spawned process

Status: Accepted; rendering verification incomplete.
Date: 2026-11-05.

## Context

GLFW initialization, window creation and event processing need the main thread.
The local HTTP app uses worker threads. Linux CI also needs rendering without
a display server.

## Decision

I use multiprocessing.get_context("spawn") in animate/render.py for both app and
CLI rendering. The child's main thread owns the graphics context. macOS uses a
hidden GLFW window. Linux uses OSMesa with PYOPENGL_PLATFORM=osmesa,
USE_MESA: True, and libosmesa6, libosmesa6-dev and libglu1-mesa.

Use a software fallback only if render-linux still fails after all three checks:

1. Import OpenGL.osmesa with PYOPENGL_PLATFORM=osmesa.
2. Run the vendored mesa_view.py in isolation with that environment.
3. Test Mesa from the runner's default apt sources.

The fallback animate/soft_render.py takes the deformed mesh from AnimatedDrawing,
warps each body-part texture with skimage.transform.PiecewiseAffineTransform and
warp in depth order, and alpha-composites it. Apply the same render golden test.

## Consequences

A child process isolates native failures and keeps one render path. It adds
startup and result-transfer overhead. The fallback is evidence-triggered;
a failure in a session without a display alone does not select a different renderer.

## Day-one evidence, 2026-11-05

The OpenGL.GL import succeeds with NumPy 2.5.4. The committed doctor's hidden
GLFW probe times out in a macOS session without a display and reports render: none; it does not
prove rendering works in a graphical session. Linux OSMesa was not run here.
The reproduction commands are in [verification notes](../verification.md#2-opengl-and-doctor).
Actual engine rendering still needs verification in a graphical macOS session
and with Linux OSMesa. I have not implemented a software fallback.
