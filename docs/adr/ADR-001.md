# ADR-001: Use CPU-only two-dimensional animal pose

Status: Accepted; CPU model timing measured; annotated evaluation pending.
Date: 2026-11-05.

## Context

AnimatedDrawings projects BVH joints onto a plane and uses bone orientation,
depth order and root offset. A side-view clip already contains this information.
A three-dimensional capture pipeline adds computation and rig requirements
without resolving a v1 need.

## Decision

I use YOLOX detection and APT-36K ViTPose ONNX inference on CPUExecutionProvider.
The modes are lightweight (YOLOX-tiny plus ViTPose-S), balanced (YOLOX-m plus
ViTPose-B, default) and accurate (YOLOX-m plus ViTPose-L, opt-in). Use accurate
offline for gallery and demo work. Exclude ViTPose-H and its external weights.
CoreML is not the v1 provider; the CPU claim must describe the actual execution.

Keep the AP-10K joint order:

| Index | Joint | Index | Joint |
| --- | --- | --- | --- |
| 0 | L_Eye | 1 | R_Eye |
| 2 | Nose | 3 | Neck |
| 4 | Root_of_tail | 5 | L_Shoulder |
| 6 | L_Elbow | 7 | L_F_Paw |
| 8 | R_Shoulder | 9 | R_Elbow |
| 10 | R_F_Paw | 11 | L_Hip |
| 12 | L_Knee | 13 | L_B_Paw |
| 14 | R_Hip | 15 | R_Knee |
| 16 | R_B_Paw | | |

Flip pairs are (0, 1), (5, 8), (6, 9), (7, 10), (11, 14), (12, 15), (13, 16).
Frames are RGB. Feed YOLOX BGR values from 0 to 255, pad with 114 and do not
normalize. Feed ViTPose RGB normalized by ImageNet mean and standard deviation.
The vendored preprocessing does not convert these colour orders for us.
These are my input conventions. The independent sources below support the pose
convention but leave a conflict for the exact detector assets unresolved.

I support Python >=3.12,<3.15 to stay within the supported wheel matrix. The
initial interpreter listing showed 3.12.16 available versus installed 3.12.15;
I have not changed that interpreter. I retain strict third-party declarations
and record any new wheel constraint here.

## Consequences

Side-view and confidence checks remain necessary; this is not three-dimensional
reconstruction. Detector colour order, animal filtering and pose flips need
regression coverage. Whole-clip processing needs timing on real frames.
The isolated random-tensor timing below is not a capture-time or cold-start claim.
If platform goldens disagree, I record measured differences and retain
separate platform goldens without widening tolerances.

## Day-one timing, 2026-11-05

Host identification via system_profiler: Apple M5, Mac17,2, 10 cores
(proc 10:4:0:6), 32 GB. macOS 27.2 arm64, CPython 3.12.15, onnxruntime 1.31.1.
The pinned ViTPose-L download is 1234459913 bytes with SHA-256
595e2a10cf20a744446b924f0cea7b9a4c7b35e4f730a148510cac863a3d8737.
Only CPUExecutionProvider was selected. Default session options, five warmups,
then 20 sequential runs of seeded random float32 input shaped (1, 3, 256, 192).
The measured median is 110.338 ms.


Reproduce from the repo root using the extraction step in docs/verification.md,
then its model-download command, followed by:

```sh
UV_CACHE_DIR=/tmp/copypaw-uv-cache uv run python /tmp/copypaw-verification/vitpose.py
```

This is the complete benchmark script; the extraction step writes it unchanged:

```python
# probe: vitpose.py
import hashlib
import platform
import statistics
import time
from pathlib import Path

import numpy as np
import onnxruntime as ort

path = Path("/tmp/copypaw-verification/vitpose-l-apt36k.onnx")
assert path.stat().st_size == 1234459913
with path.open("rb") as model:
    digest = hashlib.file_digest(model, "sha256").hexdigest()
assert digest == "595e2a10cf20a744446b924f0cea7b9a4c7b35e4f730a148510cac863a3d8737", digest
session = ort.InferenceSession(str(path), providers=["CPUExecutionProvider"])
input_data = np.random.default_rng(0).random((1, 3, 256, 192), dtype=np.float32)
feed = {session.get_inputs()[0].name: input_data}
for _ in range(5):
    session.run(None, feed)
timings_ms = []
for _ in range(20):
    start = time.perf_counter_ns()
    session.run(None, feed)
    timings_ms.append((time.perf_counter_ns() - start) / 1_000_000)
print("platform:", platform.platform(), platform.machine())
print("onnxruntime:", ort.__version__, "providers:", session.get_providers())
print("bytes:", path.stat().st_size, "sha256:", digest)
print("warmups: 5; timed runs: 20; float32 shape:", input_data.shape)
print("session options: default; sequential requests; no thread override")
print("samples_ms:", ", ".join(f"{value:.3f}" for value in timings_ms))
print(f"median_ms: {statistics.median(timings_ms):.3f}")
```

## Day-one limits

The official APT-36K full-data and annotation-only OneDrive links both returned
HTTP 403. No archive was obtained, no split filenames were observed, and no
species counts or train/validation separation are claimed. I need the official
annotations before evaluation. [Verification notes](../verification.md#4-official-annotations)
record the download URLs and split-inspection command. The multi-dataset
training configuration cited below names `train_annotations_1.json`; I exclude
that training split from evaluation.

OpenCV 5.0.0.93 decoded the synthetic ten-bit rotated HEVC fixture and passed
an adaptive-threshold/morphology smoke probe. That historical smoke result does
not establish acceptance of the separate video regression tests. I have no
measured reason to downgrade OpenCV.

## Upstream evidence

I retrieved these files on 2026-11-06 UTC. A source revision pins the text I
inspected; it does not prove that an older published binary was exported from
that revision.

- The ViTPose multi-dataset training configurations ([small](https://github.com/ViTAE-Transformer/ViTPose/blob/c050ed29112da7704797cc1a65af0234b525010d/configs/body/2d_kpt_sview_rgb_img/topdown_heatmap/coco/vitPose+_small_coco+aic+mpii+ap10k+apt36k+wholebody_256x192_udp.py), [base](https://github.com/ViTAE-Transformer/ViTPose/blob/c050ed29112da7704797cc1a65af0234b525010d/configs/body/2d_kpt_sview_rgb_img/topdown_heatmap/coco/vitPose+_base_coco+aic+mpii+ap10k+apt36k+wholebody_256x192_udp.py), [large](https://github.com/ViTAE-Transformer/ViTPose/blob/c050ed29112da7704797cc1a65af0234b525010d/configs/body/2d_kpt_sview_rgb_img/topdown_heatmap/coco/vitPose+_large_coco+aic+mpii+ap10k+apt36k+wholebody_256x192_udp.py)) use
  `ap10k_info` for the APT-36K training entry, preserve its 17 ordered channels,
  and name `data/ap36k/annotations/train_annotations_1.json`. This identifies a
  training input, not an independently inspected evaluation split.
- The [shared dataset metadata](https://github.com/ViTAE-Transformer/ViTPose/blob/c050ed29112da7704797cc1a65af0234b525010d/configs/_base_/datasets/ap10k_info.py)
  confirms the table's indices and the seven left/right swaps. `Root_of_tail`
  is my local alias for upstream `Root of tail`, not the upstream spelling.
- The export publisher's [APT-36K channel configuration](https://github.com/JunkyByte/easy_ViTPose/blob/bb9860359e55b099a507c8000e360d48a27cc36d/easy_ViTPose/configs/ViTPose_apt36k.py)
  keeps channels 0 through 16 in order for all four model sizes. Its
  [APT-36K skeleton dictionary](https://github.com/JunkyByte/easy_ViTPose/blob/bb9860359e55b099a507c8000e360d48a27cc36d/easy_ViTPose/vit_utils/visualization.py)
  names those same joints. Together these support the joint interpretation I
  use for the pinned S/B/L files; the missing binary lineage is stated below.
- The publisher's [export script](https://github.com/JunkyByte/easy_ViTPose/blob/bb9860359e55b099a507c8000e360d48a27cc36d/export.py) loads the selected dataset
  and model-size configuration and exports float input shaped `(1, 3, 256, 192)`
  with a dynamic batch dimension. The [common model configuration](https://github.com/JunkyByte/easy_ViTPose/blob/bb9860359e55b099a507c8000e360d48a27cc36d/easy_ViTPose/configs/ViTPose_common.py)
  specifies Gaussian heatmaps, size `[48, 64]`, UDP decoding and no heatmap shift.
- The publisher's [inference implementation](https://github.com/JunkyByte/easy_ViTPose/blob/bb9860359e55b099a507c8000e360d48a27cc36d/easy_ViTPose/inference.py)
  accepts RGB, divides values by 255, subtracts `[0.485, 0.456, 0.406]`, divides
  by `[0.229, 0.224, 0.225]`, then produces NCHW float32
  input. Its example expands rounded xyxy boxes by ten pixels on each side,
  clips them to the image, pads to width/height 3/4 and bilinearly resizes to
  192 by 256. The [padding function](https://github.com/JunkyByte/easy_ViTPose/blob/bb9860359e55b099a507c8000e360d48a27cc36d/easy_ViTPose/vit_utils/inference.py)
  confirms symmetric zero padding. The inference call selects unbiased UDP
  decoding; its [decoder](https://github.com/JunkyByte/easy_ViTPose/blob/bb9860359e55b099a507c8000e360d48a27cc36d/easy_ViTPose/vit_utils/top_down_eval.py)
  applies DARK refinement for Gaussian heatmaps.
- The multi-dataset training configurations above use RGB via
  [LoadImageFromFile](https://github.com/ViTAE-Transformer/ViTPose/blob/c050ed29112da7704797cc1a65af0234b525010d/mmpose/datasets/pipelines/loading.py), the same
  mean/std, UDP affine transforms, Gaussian targets with sigma 2 and UDP
  encoding for the animal pipeline. The [dataset crop implementation](https://github.com/ViTAE-Transformer/ViTPose/blob/c050ed29112da7704797cc1a65af0234b525010d/mmpose/datasets/datasets/base/kpt_2d_sview_rgb_img_top_down_dataset.py)
  expands an aspect-corrected box by 1.25. That training convention differs
  from the export publisher's ten-pixel example crop.
- The versioned [rtmlib 0.0.16 wheel](https://files.pythonhosted.org/packages/2f/e5/458732286f895e154a1ee1c371904238063d35698a155e41ecc4fd2f64f0/rtmlib-0.0.16-py3-none-any.whl), members
  `rtmlib/tools/pose_estimation/vitpose.py` and the adjacent `pre_processings.py`,
  supplies a 1.25-expanded xyxy crop, aspect correction and UDP affine warp.
  Its pixel-unit mean `[123.675, 116.28, 103.53]` and std
  `[58.395, 57.12, 57.375]` are equivalent to the RGB normalization above.
  Its decoder uses DARK and divides coordinates by heatmap size minus one.
  This confirms the consumer convention, not the exact exports' training.
- The detector's [release-tag preprocessing](https://github.com/Megvii-BaseDetection/YOLOX/blob/e1052df71842031413f6030723c3607b839c80ce/yolox/data/data_augment.py)
  pads with 114, reverses BGR to RGB and divides by 255. The
  [release-tag ONNX example](https://github.com/Megvii-BaseDetection/YOLOX/blob/e1052df71842031413f6030723c3607b839c80ce/demo/ONNXRuntime/onnx_inference.py)
  supplies ImageNet mean/std. In contrast, the rtmlib wheel's
  `rtmlib/tools/object_detection/yolox.py` keeps image channel order, pads with
  114 and does not normalize. The release-tag source and consumer therefore
  disagree; I do not treat either as proof of the downloaded assets' contract.

## Weight identity and licences

[Verification notes](../verification.md#model-file-provenance) record publisher
sizes and SHA-256 values for the exact pose files, plus independently measured
YOLOX release-asset sizes and digests.

The pinned [pose model card](https://huggingface.co/JunkyByte/easy_ViTPose/blob/e83805274e89428969355ec4afffcbc413e79188/README.md)
refers weight licensing to ViTPose's [Apache-2.0 licence](https://github.com/ViTAE-Transformer/ViTPose/blob/c050ed29112da7704797cc1a65af0234b525010d/LICENSE).
The export publisher's [code licence](https://github.com/JunkyByte/easy_ViTPose/blob/bb9860359e55b099a507c8000e360d48a27cc36d/LICENSE) is also Apache-2.0.
YOLOX's [release-tag code licence](https://github.com/Megvii-BaseDetection/YOLOX/blob/e1052df71842031413f6030723c3607b839c80ce/LICENSE) is Apache-2.0; the release
metadata does not separately state a weight licence.

Rechecked against these primary sources on 2026-11-12:

| Download | Published terms and limits of the evidence |
| --- | --- |
| `yolox_m.onnx`, `yolox_tiny.onnx`, release `0.1.1rc0` | The repository's Apache-2.0 licence permits use, modification and redistribution of the licensed work with its licence, notices and modification notices, includes a patent grant and disclaims warranty. The [release page](https://github.com/Megvii-BaseDetection/YOLOX/releases/tag/0.1.1rc0) publishes the assets but gives no explicit weight-specific grant. Applicability of those code terms to these exact binaries remains unconfirmed. |
| ViTPose S/B/L APT-36K ONNX exports at the pinned revision | The linked export publisher's model card refers weight licensing to ViTPose's Apache-2.0 terms. Binary training/export lineage remains unverified as described below. |

The [upstream weight-licensing question](https://github.com/Megvii-BaseDetection/YOLOX/issues/1915)
also has no publisher answer at this check; the question itself is not a licence.
Do not describe every downloaded weight as openly licensed or infer a commercial
redistribution grant from the repository badge. Copypaw's MIT licence covers its
own code; the model fetcher currently downloads weights without bundling licence texts.

## Not independently confirmed

- I found no export manifest tying the pinned S/B/L ONNX digests to an exact
  checkpoint digest, training configuration, exporter commit or invocation.
  The linked configurations support the intended order, flip mapping,
  normalization and heatmap convention; they do not close that binary lineage.
- The standalone APT-36K-named training configurations
  ([small](https://github.com/ViTAE-Transformer/ViTPose/blob/c050ed29112da7704797cc1a65af0234b525010d/configs/animal/2d_kpt_sview_rgb_img/topdown_heatmap/apt36k/ViTPose_small_apt36k_256x192.py),
  [base](https://github.com/ViTAE-Transformer/ViTPose/blob/c050ed29112da7704797cc1a65af0234b525010d/configs/animal/2d_kpt_sview_rgb_img/topdown_heatmap/apt36k/ViTPose_base_apt36k_256x192.py),
  [large](https://github.com/ViTAE-Transformer/ViTPose/blob/c050ed29112da7704797cc1a65af0234b525010d/configs/animal/2d_kpt_sview_rgb_img/topdown_heatmap/apt36k/ViTPose_large_apt36k_256x192.py))
  contain AP-10K annotation paths and non-UDP defaults at this revision. I
  cannot use their names as evidence of these APT-36K exports' training.
- I have not resolved whether the exact YOLOX assets require legacy RGB
  normalization or the unnormalized BGR consumer convention. I also found no
  separate publisher statement licensing those weight files, and no publisher
  SHA-256 values for them. My measured digests are not publisher attestations.
- Official APT-36K annotation contents, evaluation split separation and species
  counts remain unavailable. Pose acceptance on the walking sample does not
  establish accuracy on a trot, other animals or a labelled dataset.
